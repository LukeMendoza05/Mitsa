# Mitsa account mail

Current email-code phase: see [email-verification-implementation.md](email-verification-implementation.md), [approved isolated code capture](email-code-capture-approval.md), [activation results](code-capture-activation-results.md) and [revised Gmail/Vercel proposal](gmail-vercel-testing-proposal.md). The approved hook now retains provider-generated signup codes inside the existing encrypted capture; the application uses signup-only resend. No Resend/Gmail SMTP or external delivery was activated. Shared responsive transactional styling follows Mitsa's actual pages; provider HTML/plain-text template files and safe illustrative previews are prepared locally. The sections below describe the earlier delivery foundation and remain relevant where explicitly noted.

Current working delivery is the approved isolated encrypted capture. Supabase's strict SQL Send Email hook captures allowlisted synthetic verification/recovery messages. Invitation commands generate high-entropy tokens inside a trusted database transaction, persist only their hashes in invitation records, encrypt the message for the operator-local private key and mark the matching outbox capture atomically. Raw tokens are never returned by normal management APIs. The local private-key reader writes only ignored files; no external mail is sent.

`src/lib/mail/messages.ts` renders original Mitsa signup, recovery and invitation messages, with escaped workspace text, a fixed approved origin, expected link purpose and explicit confirmation guidance. The operator reader saves their HTML alongside the private captured JSON, only under ignored `.secrets/auth-mail/messages/`; these previews contain one-time links and must never be published or captured in screenshots. `src/lib/mail/resend.ts` uses pinned official SDK `resend@6.32.1`: trusted release/sender authorization must precede a send; an event gets a stable idempotency key and a retry window shorter than the provider's 24-hour deduplication period. API failures remain generic.

Webhook foundation verifies the unchanged raw body with the official SDK, rejects stale/tampered signatures and oversized payloads, and minimizes the resulting delivery event to provider ID, event ID/type/time and body digest. It cannot acknowledge an event before the supplied durable transaction succeeds. Signature authenticity alone is not authorization to change an unrelated outbox item. No public receiver or active worker is installed. Durable replay/known-outbox matching, terminal-state ordering, retries and suppression persistence must be implemented and reviewed before activation; these are not claimed as hosted integration.

Four local tests passed using a mocked network for the actual SDK and real cryptographic signatures. They prove rendering safety, closed-gate/no-network behavior, provider idempotency, bounded retries, tampering/expiry denial and commit failure propagation. They do not prove live Resend delivery. `npm install` reported zero known dependency vulnerabilities at installation.

Release prerequisites: approved verified sender/domain, restricted provider credentials, reviewed worker/receiver persistence, signed-webhook configuration, provider-specific suppression and retry policy, and fresh external-delivery authorization. Current public/external release gates remain false. Do not replace the strict synthetic hook with SMTP to bypass its recipient controls. SMTP/provider settings are unchanged; choosing the production Auth delivery arrangement is a separate reviewed configuration step.

Verified official references: [Next.js sending prerequisites](https://resend.com/docs/send-with-nextjs), [signature verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [idempotency window](https://resend.com/docs/dashboard/emails/idempotency-keys), [Supabase SMTP configuration](https://resend.com/docs/send-with-supabase-smtp).
