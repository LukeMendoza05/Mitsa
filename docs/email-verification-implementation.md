## Implementation

- `/verify-email` now shares the approved Mitsa desktop auth composition and responsive mobile layout, with **Verify your email.**, one accessible code input, **Verify email**, **Resend code**, a countdown, clear inline feedback and Back to sign in. No recipient is serialized into the page. Native POST works without JavaScript; the server always checks cooldown. JavaScript supplies countdown, grouped pending actions and focused network errors.
- `/auth/register` issues an authenticated encrypted, HttpOnly/Strict continuation only after authorized signed-intent/password signup. The cookie contains the recipient and bounded continuation metadata, never the code, password or verification token. Missing encryption configuration fails closed before provider signup.
- `/auth/email/code` accepts no browser-controlled email/purpose. It verifies only signup codes through Supabase Auth, requires the existing registration finalization/Terms operation and then routes to MFA or the invitation flow. It grants no membership or workspace. Already signed-in users keep their identity and go to their workspaces.
- Signup resend calls only Supabase `resend({type:'signup'})`. It does not call password recovery, passwordless sign-in or Resend's email API. A 60-second server deadline, per-recipient concurrent/replay guard and bounded verification attempts supplement provider limits. The in-memory guard is defense in depth; provider frequency/IP limits and strict hook's database-locked recipient/global limits remain authoritative across server processes/restarts. No distributed guarantee is attributed to the in-memory map.
- Supabase resend replaced the earlier code in actual hosted tests. Feedback tells users to use the latest message. An already confirmed account gets no new signup confirmation from provider resend; no new registration or factor reset is attempted for the developer.
- Unconfirmed password sign-in can recover the verification page through a new encrypted continuation. That continuation does not override provider eligibility/intent expiry or mail authorization. Long-expired provider registration intents still fail closed and require an approved recovery/renewal policy; the UI does not silently fabricate a new Terms acceptance.
- Existing `/auth/email` links remain scanner-safe: GET only stages encrypted context; explicit same-origin POST consumes the token. Signup and password recovery remain distinct. Logout clears the signup continuation. Existing routes, MFA, session cookies, CSRF, RLS, RBAC and tenant checks remain intact.
