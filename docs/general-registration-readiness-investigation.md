## Finding

Mitsa's signup implementation is functional. Its completed controlled journey already used an ordinary, unallowlisted address and passed email verification, trusted MFA, atomic workspace creation, Business Owner access and returning sign-in.

Continuous registration is unavailable because the implementation still uses the earlier **bounded pilot admission and delivery system**. The database pilot is closed, its private local runtime expired, and its worker heartbeat is stale. The general-phase operator additionally requires recovery evidence in a particular onboarding record and a strict terminal refresh-reuse guarantee that has not passed.

The refresh finding is a session-compromise concern. It is **not a Supabase technical prerequisite for creating an account**, and no evidence shows that it bypasses signup CAPTCHA, creates an Owner membership, or crosses tenants. Keeping it as an absolute registration prerequisite is an application security-policy decision. Changing that decision requires explicit approval; this report does not change the gate or turn its failed regression green.

## Refresh-family assessment

### What actually failed

The refined synthetic tests rotated four distinct tokens, waited 12 seconds (outside the configured 10-second reuse period), then reused a non-parent old ancestor. Supabase returned HTTP 400 / `refresh_token_already_used`. Immediately afterward every refresh record in that family was revoked, but the session row remained. Trying the latest token immediately could issue a replacement; waiting another 12 seconds in the separate reproduction caused rejection. The old bearer was accepted in both cases. See the two hashed `refresh-reuse-*-post-revocation-interval.json` records.

That is a demonstrated gap against Mitsa's **immediate and permanent terminal-family denial** test. It is not evidence that an unauthenticated person can manufacture a session or bypass another tenant's membership. The demonstration uses existing synthetic session credentials; a stolen authenticated AAL2 bearer can carry that victim's existing permissions. MFA and tenant isolation do not make that bearer harmless.

Normal refresh grace and immediate-parent retries are deliberate provider behavior. A previously issued JWT staying valid until expiry is also documented. However, the observed replacement after a detected out-of-window ancestor replay should not simply be declared expected: the documented termination description and legacy implementation need provider clarification. Current upstream source pinned to the reported release is consistent with the observation, but it is not a checksum of the hosted binary. A newer-token branch differs; no supported hosted switch has been established. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [signout semantics](https://supabase.com/docs/guides/auth/signout).

Classification: confirmed failure of the selected guarantee; conditional compromised-session exposure; partly ordinary JWT behavior, partly unresolved provider behavior. **Not a confirmed cross-tenant exploit, not a signup implementation failure, and not proof that continuous development registration is impossible.** It remains a blocker under the existing unmodified policy because the user has not accepted a different criterion.

## Sustainable implementation proposal — disabled first

Keep the current Next.js, Supabase Auth, signed intents, capture queue, SMTP adapter, MFA and workspace/RBAC implementation. Do not rename the production mode or turn all public release gates on.

1. **Introduce a separate persistent isolated-development control.** Proposed one private singleton table `private.development_registration_control`, disabled by default: approval generation, exact project/origin, `admission_enabled`, `delivery_enabled`, worker `healthy_until`, approved sender fingerprint and OTP configuration. Force RLS; no browser/service-role writes; limited reads for the existing policy and Auth-hook roles. Retain the old pilot row/ledger unchanged for historical evidence. Remove the 30/120-minute human deadline only from the new mode. A 60-second renewable health timeout remains fail closed after crashes; it is not a recurring user approval window.
2. **Add restricted admission and delivery helpers.** Admission requires enabled control, correct marker/origin, test agreement, healthy service and available budget. Delivery separately requires its switch, health/budget and an eligible account's original signed intent. Existing production gates remain false. An admission stop must not automatically revoke delivered OTPs, current accounts or sessions.
3. **Modify only development eligibility branches** in `mitsa_registration_policy`, `mitsa_registration_intent`, `mitsa_before_user_created`, `mitsa_isolated_send_email`, and `mitsa_development_recovery_allowed`. Preserve signature/replay/nonce/provider identity/Terms/expiry checks, owners, grants, search paths and role boundaries. Do not replace the existing Auth pointers or bypass hooks. Existing tests continue using the old synthetic path. Ordinary new recipients qualify through the new admission branch, not a recipient list.
4. **Change local runtime and operator service** in `development-registration.ts`, `registration.ts`, `registration-policy.ts`, `isolated-registration-service.mjs`, `development-mail-lease.ts`, `development-mail.mjs`, and `pilot-mail-claim.ts`. Use persistent activation generation and health, no manual deadline or per-run 20-message ceiling in continuous mode; retain 10/hour, 20/rolling24-hour and recipient-minute durable caps. The operator remains separate from Next, with no database/admin/SMTP credentials in the ordinary app. A Windows-current-user supervised process is sufficient locally; sleep/offline pauses admission. No Vercel service is needed.
5. **Separate account continuation** in login, verification-page/code route and password-request route. A password-proven pending account with valid original intent can resume verification while admission is closed. Resend/recovery still require separately authorized healthy delivery and budgets. Already-delivered valid codes remain verifiable after admission closes. An expired sealed flow or 24-hour intent requires an explicit secure renewal path; do not extend it silently or create a duplicate account. Keep generic recovery responses and MFA.
6. **Handle quota/delivery failures accurately.** Readiness is not SMTP delivery proof. Use durable capture/claim state and budget checks before admitting mail work, serialize competing requests, pause new admission when insufficient capacity, and preserve pending-account continuation when provider errors leave a pending identity. Never blindly retry an uncertain SMTP claim or send the old code after service restart. Explicit user resend creates a fresh provider message. Preserve encrypted capture and minimal logs; build a separately reviewed retention cleanup for expired secret payloads rather than claiming the current queue automatically purges them.
7. **Make the evidence ledger scope-aware.** Reference independent captured-recovery tests as such, rather than requiring a reset of Yuno. Keep real ordinary-address recovery delivery pending until an expressly approved test. Replace the single strict general-mode evidence gate only after the user selects a session-security policy; keep the failed terminal-reuse regression visible.
8. **Verify the changed boundaries before activation.** Offline PostgreSQL tests for admission/delivery separation, role/nonce/consent binding, quota races, worker stop/restart, stale generations and rollback; negative direct Auth/Edge probes under the new eligibility branch; ordinary unallowlisted signup/OTP/MFA/workspace and returning sign-in only to cover changed behavior; independent tenant and sensitive-command checks. Existing retained accounts are preservation targets, not test fixtures.

This is medium-complexity work concentrated in admission/worker state and five existing SQL bodies. The authentication/onboarding architecture does not need rebuilding. Global provider CAPTCHA rollout, external recovery delivery, a new transactional provider or a session-age cap are separate medium-complexity changes; the provider's terminal-reuse correction has unknown effort and timing. These are relative implementation estimates, not a delivery promise.

### Exact provider configuration proposal

For the smallest continuous-development candidate: **no Supabase setting change is intrinsically required**. Keep signup enabled, confirmation mandatory, anonymous off, OTP six digits/3,600 seconds, current rotation/reuse settings, current strict Before User Created and Send Email pointers, and all production gates closed. Read the nonsecret dashboard settings first to close the configuration-observation gaps; do not request keys in chat.

If global Supabase CAPTCHA is still required as an additional defense, prepare a separate compatibility change for signup, password sign-in, recovery and applicable resend paths. The current app consumes the signup proof before calling Supabase and passes no fresh provider proof; enabling the toggle now is unsafe. Each proof must have one validation owner, or independent fresh proofs must be used. The signed-intent protection must remain, including protection against direct Auth calls. ## Rollback and incident controls

For the proposed continuous mode, shutdown must be an authenticated operator action on Mitsa-owned private controls: first disable new admission, then independently disable external delivery when needed; stop the supervised worker and invalidate its health generation. Verify direct signup without an already authorized valid flow is rejected and delivery claims stop. Preserve the pending accounts, consent/intents, encrypted evidence and delivery ledger. Existing valid OTP verification should remain possible without new mail.

The migration package must include the exact previous function definitions/ACL hashes and an encrypted preservation baseline, all-new controls initially disabled, and rollback that restores only changed definitions with continuous controls closed. Retain historical tables rather than deleting evidence. No rollback may write managed Auth records, reset users/MFA, transfer ownership or restore old memberships. Closing registration or delivery is **not session revocation**. Any incident requiring session revocation uses supported Auth APIs and separate account-specific authorization.

The future service must resume after an ordinary outage only under an existing persistent approval generation. Emergency stop clears that generation; auto-restart must not undo an operator stop. Test quota recovery, old-message filtering and stale worker ownership before enabling it.
